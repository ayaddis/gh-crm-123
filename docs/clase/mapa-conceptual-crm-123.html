El mapa general

CRM-123 es un sistema pequeño para un equipo comercial de pólizas de seguros en México: 10 vendedores y 2 supervisores. Son dos aplicaciones, una base de datos y un robot que manda el resumen de las 7:30. Cada color es un tipo de pieza.

Cómo fluye todo

Dos recorridos que conviene entender bien: cómo el código llega a internet y qué pasa, paso a paso, cuando se manda el resumen.

A. Del código a la aplicación en línea

Trampa frecuente: el botón Redeploy de Vercel reutiliza el código anterior. Sirve solo cuando cambiaste variables de entorno. Para publicar código nuevo hay que abrir el Deploy Hook. Y cualquier variable nueva solo se aplica en un despliegue nuevo.

B. El resumen de las 7:30, paso a paso

  1. Pasos 1 a 3, arranque: alguien pulsa el botón y la aplicación avisa a n8n.
  2. Pasos 4 a 6, recolección: n8n pide los datos y la aplicación los busca en la base.
  3. Pasos 7 y 8, envío: n8n pide a Resend un correo por persona.
  4. Pasos 9 a 11, cierre: n8n reporta, la aplicación guarda el resultado y lo muestra.
Cuando lo dispara el reloj de las 7:30 no hay supervisor ni botón: n8n arranca solo en el paso 4. Si el interruptor de envío automático está apagado, la aplicación responde "omitido" y el flujo termina sin mandar nada.

Seguridad en capas

Principio central: la interfaz oculta lo que no te toca, pero la seguridad real está en la base de datos. Aunque alguien manipule la pantalla, la base no le entrega lo que no es suyo.

Capa 1

Base de datos

Qué hay
Permisos por fila (RLS) en todas las tablas. No existe borrado físico: se archiva. El historial y las actividades solo admiten altas. Las vistas respetan los permisos de quien consulta.
Qué evita
Que un vendedor vea a los clientes de otro, se quede con una oportunidad ajena o borre rastro.
Capa 2

Aplicación

Qué hay
La llave maestra vive solo en el servidor y solo en rutas autorizadas. La persona se identifica con getUser() y su rol se lee de la tabla profiles, nunca de algo que mande el navegador. Los secretos se comparan en tiempo constante.
Qué evita
Que una llave se filtre al navegador o que alguien se haga pasar por supervisor.
Capa 3

Integraciones

Qué hay
n8n nunca toca la base: solo usa la API de la aplicación con su propio secreto. Ningún secreto se guarda en GitHub ni en los registros. El envío manual tiene espera de 120 segundos y cada solicitud se usa una sola vez.
Qué evita
Envíos duplicados, llamadas falsas al flujo y fugas por registros o capturas.
Capa 4

Proceso de trabajo

Qué hay
Un hito a la vez, con confirmación escrita antes de avanzar. Una prueba automática de seguridad (check:security) corre en cada cierre. La IA no modifica la base de datos.
Qué evita
Que el error de una etapa se arrastre a la siguiente o que una "mejora" rompa una regla sin que nadie lo note.

Lo que nos enseñaron los tropiezos

Los errores del ejercicio fueron la mejor parte de la clase. Cada uno deja una regla práctica.

Qué pasóEl primer despliegue falló por no tener las variables de entorno.
Qué aprendimosLas variables deben existir antes de compilar. La app falla a propósito si faltan, para no arrancar a medias.
Qué pasóUn cambio ya subido a GitHub no aparecía en línea.
Qué aprendimosRedeploy reutiliza el código viejo. Para código nuevo se usa el Deploy Hook.
Qué pasóEl envío falló con "n8n respondió 403".
Qué aprendimosUn 403 o 401 casi siempre es un secreto que no coincide entre dos sistemas. Hay dos secretos distintos y cada uno va en su propio lugar.
Qué pasóEl flujo salió en verde pero no mandó ningún correo.
Qué aprendimosVerde no es sinónimo de funcionó. Hay que abrir la salida de cada nodo y comprobar el resultado real.
Qué pasóLa propia aplicación mandaba a n8n a la pantalla de inicio de sesión.
Qué aprendimosLas rutas que usa un robot se protegen con un secreto, no con una sesión de persona. Una prueba real lo reveló.
Qué pasóUna llave secreta se vio en una captura de pantalla.
Qué aprendimosUna captura también es una fuga. Los secretos se marcan como secretos y se tapan al compartir.
Qué pasóUna variable escrita como "True" con mayúscula dejó el modo de pruebas inválido.
Qué aprendimosLos valores de configuración se escriben exactos, y la app avisa cuál variable falta sin mostrar su valor.
Qué pasóSe avanzó de etapa sin tener los resultados reales de las pruebas.
Qué aprendimosCada hito se cierra con pruebas hechas y confirmadas, no con suposiciones. Mejor validar directo en la base cuando se puede.

Glosario rápido

Las palabras técnicas que aparecieron, en lenguaje de todos los días.

RLS (permisos por fila)
Regla de la base que decide, fila por fila, quién puede ver o cambiar un dato.
API
La ventanilla por la que un programa le pide cosas a otro.
Webhook
Una dirección que, al recibir un aviso, pone en marcha un flujo.
Variable de entorno
Un dato de configuración guardado fuera del código, como una llave o una dirección.
Secreto
Una variable que no debe verse ni compartirse, como una contraseña.
Deploy Hook
Un enlace que, al abrirlo, ordena a Vercel publicar la última versión.
PWA
Un sitio web que se instala en el celular y se usa como aplicación.
Hito
Una etapa del proyecto que se prueba y se confirma antes de seguir.
Historial (audit log)
Un registro donde solo se agregan líneas. Nadie puede editarlo ni borrarlo.
Modo de pruebas
Un interruptor que manda todos los correos a una sola cuenta para no molestar a nadie.
